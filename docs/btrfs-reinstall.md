# Reinstall `nixos` on btrfs

The disk layout is declared, not typed: `modules/storage/filesys.nix` holds the
`disko` definition, and the same file both drives the install and generates the
`fileSystems` of the running system. There is no UUID to look up, no
`nixos-generate-config` output to copy, and no partitioning command to run by
hand.

Layout:

| Partition | Size | FS    | Mount       | GPT label    |
| --------- | ---- | ----- | ----------- | ------------ |
| `p1`      | 1G   | vfat  | `/boot` ESP | `nixos-boot` |
| `p2`      | rest | btrfs | subvolumes  | `nixos-root` |

Subvolumes on `p2`: `@` → `/`, `@home` → `/home`, `@nix` → `/nix`, `@log` →
`/var/log`. All mounted with `compress=zstd:3,noatime`.

Every mount resolves through `/dev/disk/by-partlabel/<label>`, so the config
survives a reformat and never refers to a filesystem that no longer exists. No
default subvolume is set and none is needed: every mount names `subvol=`
explicitly, so a bare `mount /dev/nvme0n1p2` in a rescue shell lands on the top
level, not on `@`.

No swap partition: `zramSwap` is enabled and hibernation is not configured. No
LUKS, no snapper.

## 0. What you need at hand

- The NixOS ISO on a stick (`dd if=nixos-*.iso of=/dev/sdX bs=4M
  status=progress oflag=sync`, or drop it on a Ventoy stick).
- The backup of `~/.config/sops/age/keys.txt`. Without it the sops secrets
  (and the `jiwolfsly`/`dummy` passwords) are unreadable.
- Whatever else you want back: `~/.ssh/id_ed25519*` and `allowed_signers`,
  `~/.secrets/agents`, `~/.local/share/ai-memory`, `~/projects`,
  `~/Documents/sb`, `~/Jellyfin`, `~/Pictures/Wallpapers`,
  `/var/lib/libvirt/images/win11.qcow2`, other `/var/lib` service state.
- The flake is on **`develop`**; `master` is a different lineage and does not
  contain the btrfs config. The clone below pins the branch.
- The branch has to be pushed. Flakes only see **git-tracked** files, and the
  live ISO clones from GitHub.

## 1. Boot the live ISO

Boot in **UEFI** mode — `boot.loader.efi.canTouchEfiVariables` needs
`/sys/firmware/efi`:

```bash
[ -d /sys/firmware/efi ] && echo UEFI || echo "booted in BIOS mode, reboot"
```

Get network (needed for the clone and the binary cache):

```bash
nmtui          # or: iwctl, then systemctl start NetworkManager
ping -c1 cache.nixos.org
```

Identify the target disk and the backup stick:

```bash
lsblk -f
```

## 2. Clone the flake and put the sops key in place

```bash
mkdir -p /backup && mount /dev/<backup-stick>1 /backup

mkdir -p /mnt/home/alsoasnerd/.config
git clone -b develop https://github.com/alessandromalacarne/nixos.git \
  /mnt/home/alsoasnerd/.config/nixos

install -D -m600 /backup/keys.txt \
  /mnt/home/alsoasnerd/.config/sops/age/keys.txt
```

`git` is part of the installer image (`installation-cd-base.nix` sets
`programs.git.enable`), so there is nothing to install first.

The clone and the key are root-owned at this point; ownership is fixed in step
5, after the install has created the user accounts. sops-nix runs as root during
`nixos-install`, so it can read the key regardless.

## 3. Check the disk name

`disko.devices.disk.main.device` is the only hardware-specific value in the
layout, and it is only read by the destructive script below. Confirm it matches
this machine:

```bash
lsblk -o NAME,SIZE,MODEL,SERIAL /dev/nvme0n1
```

If the disk is not `nvme0n1`, fix that one line in
`modules/storage/filesys.nix` and commit before installing — the config and the
disk have to name the same device.

## 4. Partition, format and mount

Everything on `nvme0n1` is destroyed from here on.

Built from the flake's own pinned `disko`, so the script that writes the disk is
generated by the same revision that configures the system — no second tool, no
version drift.

```bash
cd /mnt/home/alsoasnerd/.config/nixos
nix build .#nixosConfigurations.nixos.config.system.build.destroyFormatMount
less result/bin/disko-destroy-format-mount   # the whole plan, readable
sudo ./result/bin/disko-destroy-format-mount
```

It prints the disks it is about to destroy and asks for `yes`. The script:

- clears the partition table on the disk in `disko.devices.disk.main.device`,
- creates a 1G EF00 partition labelled `nixos-boot` and the rest labelled
  `nixos-root`,
- runs `mkfs.vfat` / `mkfs.btrfs` and creates `@`, `@home`, `@nix`, `@log`,
- mounts them at `/mnt` in dependency order with the declared options.

```bash
lsblk -f
ls -l /dev/disk/by-partlabel
findmnt -R /mnt
```

## 5. Check the hardware module, install

The repo's `hardware-configuration.nix` was generated on this machine and
already has no `fileSystems` block — `modules/storage/filesys.nix` owns the
mounts. Keep it that way. The manual is explicit that the generated file is
overwritten by every `nixos-generate-config` run and "thus, you generally
should not modify it", so treat the repo copy as the source of truth and do not
copy the fresh one over it: that would reintroduce `fileSystems."/"` and
`swapDevices`, which then conflict with `filesys.nix` (two definitions of `/`
with different devices fail evaluation).

Run the generator only to confirm the hardware has not changed:

```bash
nixos-generate-config --root /mnt
diff -u /mnt/home/alsoasnerd/.config/nixos/hardware-configuration.nix \
        /mnt/etc/nixos/hardware-configuration.nix
```

Port only genuine hardware differences (kernel modules, the microcode line)
into the repo file. Ignore the generated `fileSystems` block and `swapDevices`.

```bash
nixos-install --root /mnt --no-root-passwd \
  --flake /mnt/home/alsoasnerd/.config/nixos#nixos

nixos-enter --root /mnt -c \
  'chown -R alsoasnerd:users /home/alsoasnerd && passwd alsoasnerd'
```

`nixos-install` runs the new system's activation inside `nixos-enter`
(`switch-to-configuration boot`), which is why the sops key has to be in place
before this step. `--no-root-passwd` is fine because `alsoasnerd` is in `wheel`;
the `passwd` call is needed because no password is declared for that user.

It also evaluates the flake in **pure** mode (no `--impure`), so the config
must not read `NIX_PATH`: `<nixos-unstable>` and friends are invisible on the
ISO. This repo imports `unstable` from the flake input instead.

The users have no explicit `uid`, so a fresh install assigns 1000 and up in
alphabetical order: `alsoasnerd` stays 1000, but `dmyna`/`dummy`/`jiwolfsly`/
`public` land on different numbers than today. Re-`chown` restored data that was
copied with numeric owners.

```bash
umount -R /mnt
reboot
```

Remove the stick. If the firmware does not offer the new entry, the ESP has
`EFI/BOOT/BOOTX64.EFI` as fallback.

## 6. First boot

- Log in as `alsoasnerd` with the password set in step 5.
- `sudo nixos-rebuild switch --flake .#nixos` (or `nh os switch`) to confirm the
  flake evaluates from the new system. No `--impure` needed — the flake
  evaluates purely, which is what `nixos-install` already relied on.
- `btrfs filesystem usage /` and a compression sanity check:
  `btrfs filesystem du -s /nix/store` versus `du -sh /nix/store`.
- `sudo tailscale up` — the machine key is new, so the node re-registers.
- SSH host keys are regenerated: drop the old `known_hosts` entries on the
  machines that reach this host.

## 7. Restore data

`/var/lib/libvirt/images` already carries `+C` from `systemd.tmpfiles.rules`
(the `d` line creates the directory, the `h` line sets the attribute), so the
qcow2 restored below is written without COW from the start. Anything else that
wants it — `/var/lib/postgresql` for databases, `/var/lib/containers/storage`
for podman overlay storage — needs the same two-line pair in
`modules/storage/filesys.nix`. Pre-empting those with a `d` line is not
obvious: both directories are created by their own services with their own
ownership, so check that before adding one.

`btrfs(5)` applies `nodatacow` filesystem-wide from the first mounted subvolume,
so it cannot be a per-subvolume mount option; the inode attribute is the only
lever, and it has to be set before the files exist.

Then restore `~/projects`, `~/Documents/sb`, `~/Jellyfin`, the libvirt domain
XML plus `win11.qcow2`, and any other service state, and fix ownership:

```bash
sudo chown -R alsoasnerd:users /home/alsoasnerd
```

## Migrating an existing install (no reinstall)

A disk installed by the previous manual runbook already has the same layout; it
differs only in *identity* — its config names the filesystem by UUID, the new
one by GPT label. Align them instead of reinstalling:

```bash
lsblk -o NAME,PARTLABEL,UUID /dev/nvme0n1

sudo sfdisk --part-label /dev/nvme0n1 1 nixos-boot
sudo sfdisk --part-label /dev/nvme0n1 2 nixos-root
sudo udevadm trigger --subsystem-match=block
sudo udevadm settle
ls -l /dev/disk/by-partlabel
```

Then switch the config over and reboot with `nixos-rebuild boot --flake .#nixos`
rather than `switch`. This is safe to roll back: renaming a partition leaves the
btrfs UUID untouched, so the previous generation's `/etc/fstab` still resolves
and is selectable from systemd-boot.

If the boot with partlabels fails, nothing was reformatted — the flake was
adopted, the filesystem was not rebuilt. `lsblk -o PARTLABEL`,
`btrfs subvolume list /` and `mount -o subvol=@` from the ISO are enough to
recover without wiping the disk.

If you ever do the partitioning by hand again, note that on GPT the word after
`mkpart` is the partition **name**, not a type (`parted(8)`: *part-type may be
specified only with msdos and dvh partition tables*), so `mkpart primary …`
would only label the partition "primary".
